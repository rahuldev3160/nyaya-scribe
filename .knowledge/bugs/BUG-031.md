# BUG-031 — GS Mains paper dropdown snaps back to previously-viewed paper

**Status:** FIXED | **Severity:** HIGH | **Session:** S47 | **Category:** navigation

## Symptom
On `/upsc/mains`, selecting GS Paper II/III/IV in the "Paper" dropdown silently reverts to GS Paper I.

## Root Cause
`upsc_mains.html`'s paper `<select>` and topic `<select>` both auto-submit the same GET form on `onchange`. When the user changes only the paper dropdown, the topic dropdown still holds its stale selected value (a topic belonging to the *old* paper) — that value gets submitted alongside the new `paper` param.

`upsc_bp.py::mains()` has "auto-detect correct paper" recovery logic (for the case where someone links directly to a topic_id under the wrong paper): if `topic_id not in topic_opts` for the requested paper, it looks up which paper the topic actually belongs to and **overrides `paper` back to that value**. This recovery logic was firing on every ordinary paper switch, since the leftover topic param always looks "wrong" for the newly selected paper.

## Fix
`web/templates/upsc_mains.html` — paper `<select>`'s `onchange` now clears the topic select's `name` attribute before submitting, so no stale `topic` param is sent at all. The backend then falls through to `default_topic` for the newly selected paper instead of running its (now correctly unused) recovery path.

## File
`web/templates/upsc_mains.html` (line ~25)

## Rule Going Forward
Any form with a "recovery/auto-correct" branch that infers intent from stale params must be paired with client-side logic that actually clears those stale params on the field that triggered the change — otherwise the recovery logic and the ordinary-use case collide indistinguishably.
